Superpowers 与 OpenSpec 结合实践

当 AI 编码助手能在一分钟内生成上千行代码时，”写得快”已经不是瓶颈——“写得对”才是。Superpowers 和 OpenSpec 分别从 行为纪律 和 工件结构 两个维度解决这个问题。本文将深入探讨两者的设计哲学、核心能力，以及如何将它们结合成一套完整的 AI 开发工作流。

一、问题：AI 编码的”信任鸿沟”

用 AI 写代码，你一定遇到过这些情况：

  • AI 跳过了需求澄清，直接开始写一整套你根本没要的功能
  • 改一个 bug，AI 引入三个新 bug
  • AI 声称”完成了”，但你发现测试根本没跑通
  • 代码能跑，但架构一团糟，后续维护成本爆炸

这些问题的根源是一致的：AI 擅长生成，但不擅长纪律。 而软件开发的核心，恰恰是纪律——理解需求、设计方案、编写测试、验证结果、持续迭代。

Superpowers 和 OpenSpec 分别用不同的思路来解决这个问题。

二、Superpowers：给 AI 装上”工作流操作系统”

2.1 它是什么

Superpowers 是由 Jesse Vincent（Prime Radiant）创建的一套 AI 编码代理的软件开发方法论，以 Claude Code 插件（也支持 Codex、Gemini CLI、Cursor 等平台）的形式发布。

它的核心思想可以概括为一句话：“在任何行动之前，先检查是否有适用的技能（Skill）。”

2.2 内置 Skills 全景

Superpowers 目前提供 13 个 Skills，覆盖软件开发的完整生命周期：

阶段 Skill 触发时机 类型
启动 using-superpowers 每次会话开始 Meta
理解 brainstorming 任何创造性工作前 Process
规划 writing-plans 设计方案确认后 Process
环境 using-git-worktrees 需要隔离工作区时 Process
实现 test-driven-development 编写任何功能/修复代码前 Rigid
实现 subagent-driven-development 执行多任务计划时 Process
实现 executing-plans 单会话顺序执行计划 Process
实现 dispatching-parallel-agents 存在2+独立任务时 Process
调试 systematic-debugging 遇到任何 bug/测试失败 Rigid
验证 verification-before-completion 声称完成/修复/通过前 Rigid
审查 requesting-code-review 任务完成或合并前 Process
审查 receiving-code-review 收到 code review 反馈时 Process
收尾 finishing-a-development-branch 所有任务完成时 Process

Rigid（刚性）vs Flexible（柔性）：刚性 Skills 要求严格遵循（如 TDD 要求先写测试，调试要求先找根因），柔性 Skills 可以根据上下文调整。

2.4 关键机制：Red Flags 表

Superpowers 最有特色的设计之一，是每个 Skill 内置的 Red Flags（红旗）表。它列举了 AI 最常见的”偷懒借口”：

你可能会想… 但真相是…
“这只是个简单问题” 问题也是任务，请检查 Skills
“我需要更多上下文” Skill 检查在澄清问题之前
“让我先探索代码库” Skills 告诉你如何探索，先检查
“这不需要正式技能” 如果存在 Skill，就用它
“我记得这个 Skill” Skills 会更新，读当前版本
“我这次跳过 TDD 吧” 停止。这是合理化借口

这种设计直接对抗了 AI 的”走捷径”倾向，是 Superpowers 纪律性的核心。

三、OpenSpec：以”规格”为单一事实来源

3.1 它是什么

OpenSpec 是 Fission-AI 创建的 spec-driven development (SDD) CLI 工具。它的核心理念是：

在写任何代码之前，人和 AI 先共同商定一份规格说明（spec）。这份 spec 成为机器可读的”合同”，约束 AI 的代码生成行为。

3.2 核心概念：双文件夹模型

这个模型就像 Git 的分支机制：specs/ 是 main 分支（事实来源），changes/ 是 feature 分支（提案与实现）。归档时，增量规格会合并回主规格。

3.3 四个核心工件

3.4 命令体系

OpenSpec 提供了一套完整的命令行工具和斜杠命令：

命令 阶段 作用
/opsx:explore 探索 调研代码库，不创建正式变更
/opsx:new 创建 脚手架一个新的 change 目录
/opsx:continue 规划 逐步创建下一个工件
/opsx:ff 规划 快速生成所有规划工件
/opsx:propose 规划 一步生成 proposal + specs + design + tasks
/opsx:apply 实现 按 tasks.md 逐项实现
/opsx:verify 验证 三维度验证（完整性、正确性、一致性）
/opsx:sync 整合 将 delta specs 同步到主 specs
/opsx:archive 归档 最终完成、合并并归档变更
/opsx:bulk-archive 归档 批量归档多个变更（含冲突检测）
/opsx:onboard 引导 15 分钟交互式上手教程

3.5 设计特点

Brownfield-first（存量项目优先）：不像很多 spec 工具只能用于 0→1 的新项目，OpenSpec 专门为修改现有代码库（1→n）做了优化。增量规格（ADDED/MODIFIED/REMOVED）让变更的影响范围一目了然。

工具无关：支持 21+ 种 AI 编码助手，包括 Claude Code、Cursor、Windsurf、Gemini CLI、GitHub Copilot、Cline、RooCode 等。

四、Superpowers vs OpenSpec：对比与互补

4.1 核心差异

维度 Superpowers OpenSpec
定位 AI 的行为操作系统 SDD 工件管理系统
关注点 HOW — AI 如何工作 WHAT — 生产什么工件
形式 Claude Code 插件 npm 全局 CLI 工具
触发方式 自动（Skill 按场景激活） 手动（执行斜杠命令）
核心理念 TDD + 系统化 + 证据驱动 Spec 作为人机之间的合同
输出物 设计文档 + 实现计划 + 测试 + 审查报告 proposal / specs / design / tasks
跨平台 Claude Code / Codex / Gemini CLI / Cursor 等 Claude Code / Cursor / Windsurf / Copilot 等 20+

4.2 用一句话理解

  • Superpowers 让你的 AI 学会”写代码之前先思考，写完代码要验证，出问题先找根因”。它是一套行为素养。
  • OpenSpec 让你的 AI 和你在写代码之前先签一份”合同”，明确要做什么、怎么判断做完了。它是一套工件标准。

4.3 为什么它们互补

它们天然互补，因为解决的是同一个问题的不同层面：

  • 没有 OpenSpec，Superpowers 的”brainstorming → plan”过程缺乏结构化的持久存储——设计讨论可能丢失在聊天记录中。
  • 没有 Superpowers，OpenSpec 的 spec/tasks 文件只是一个静态清单——AI 可能跳过需求直接编码，或者修 bug 时引入新问题。
  • 两者结合，OpenSpec 提供持续可追溯的工件，Superpowers 确保 AI 在每个环节遵循正确的纪律。

5.2 各阶段的责任分工

阶段 OpenSpec 负责 Superpowers 负责
探索 提供探索命令 (/opsx:explore)，创建变更目录 通过 brainstorming Skill 引导需求澄清对话
规格 结构化 proposal、specs 增量、design 文件 提供设计评审的对话框架，确保不跳过细节
规划 提供 tasks.md 模板作为实现清单 生成精确到文件路径和代码片段的实现计划
实现 /opsx:apply 驱动按 tasks.md 执行 TDD 纪律 + 子代理调度 + 任务间审查
验证 三维度验证（完整性、正确性、一致性） 证据驱动的验证——跑测试、看输出、确认通过
归档 /opsx:archive 合并 specs 并归档 决定合并策略（merge/PR/保留/丢弃），清理环境

5.3 为什么这样设计分工

这个分工遵循一个简单的原则：OpenSpec 管”死”的东西（文件、结构、追踪），Superpowers 管”活”的东西（对话、决策、纪律）。

  • 文件不会丢：OpenSpec 的 openspec/ 目录是整个项目的审计日志，任何时候都能回溯”做了什么、为什么”。
  • 纪律不会松：Superpowers 的自动触发机制确保每次开发都走完整流程，AI 没有机会走捷径。
  • 平台可切换：如果你换了一个不支持 Superpowers 的 AI 工具，OpenSpec 的 specs 文件仍然在，仍然可以约束 AI。如果你换了一个不支持 OpenSpec 的项目，Superpowers 的纪律仍然在，仍然保证开发质量。

七、进阶：两者关系的本质

7.1 OpenSpec 是”合同”，Superpowers 是”执行纪律”

想象一个建筑工地：

  • OpenSpec 是施工图纸和合同：定义了要建什么、标准是什么、验收条件是什么。图纸一旦签字，施工方和甲方都以此为凭。
  • Superpowers 是施工规范和监理流程：规定了必须按什么顺序施工（先打地基再砌墙）、每个环节如何验收、出了问题如何追溯。没有这些规范，再好的图纸也可能盖出豆腐渣工程。

7.2 OpenSpec 补 Superpowers 的短板

Superpowers 的一个痛点是：设计文档和计划存在 docs/superpowers/specs/ 和 docs/superpowers/plans/ 中，是独立的 markdown 文件，缺乏结构化的变更追踪。 当你回溯”三个月前那个登录重构是谁提议的、规格是什么”时，只能翻聊天记录或文档文件。

OpenSpec 的 changes/ 目录结构 + specs/ 主规格目录解决了这个问题。每个变更的完整历史——从提案到归档——都有清晰的文件记录，且 delta specs 清楚地标记了增删改。

八、总结

维度 只用 Superpowers 只用 OpenSpec 两者结合
纪律性 ✅ 强 ❌ 依赖 AI 自觉 ✅ 强
可追溯性 ⚠️ 存在文档中 ✅ 结构化追踪 ✅ 完整审计
跨工具 ⚠️ 部分支持 ✅ 20+ 工具 ✅ 灵活切换
易上手 ✅ 自动触发 ⚠️ 需学习命令 ⚠️ 初期有学习成本
维持成本 ✅ 低（自动化） ⚠️ 需手动归档 ⚠️ 需遵守衔接规则
适合场景 日常开发、bug 修复 中大型功能、团队协作 所有场景

最终，这套融合工作流的目标是：

让 AI 不仅能写代码，更能像一个有纪律的资深工程师一样工作——先理解需求，再设计方案，写测试，写代码，验证结果，记录变更，最后归档。每一步都可追溯，每一步都有纪律。

软件开发中最贵的从来不是写代码的时间，而是修复错误决策的成本。Superpowers + OpenSpec 的组合，正是为了把错误决策扼杀在摇篮里。
