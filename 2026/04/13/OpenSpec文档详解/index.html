OpenSpec 文档体系与归档机制详解

使用 OpenSpec 一段时间后，openspec/ 目录下的文档会越来越多。这篇文带你彻底搞清：OpenSpec 生成了哪些文档、各自什么作用、归档到底干了什么、多需求并行会不会乱、历史文档能不能删。

一、OpenSpec 生成的所有文档

一个完整的 OpenSpec 项目结构：

逐文件说明

文件 谁生成 作用 里面有什么
config.yaml openspec init 指定 AI 工具类型、自定义 schema tools: claude 等配置项
specs/<领域>/spec.md 归档时自动合并 系统的权威规格，描述系统”当前是什么样” 按场景组织的需求描述，是所有变更的目标态
changes/<名>/proposal.md 人 + AI 协作 解释为什么改、改什么 问题背景、变更范围、影响评估
changes/<名>/.openspec.yaml 脚手架生成 变更的元数据 变更名、创建时间、状态
changes/<名>/specs/<领域>/spec.md AI 根据需求生成 增量规格——相对于主 specs 的 diff 用 ## ADDED、## MODIFIED、## REMOVED 标记的增量
changes/<名>/design.md AI 生成（可选） 技术方案——怎么做 架构决策、技术选型、数据流、API 设计
changes/<名>/tasks.md AI 或人拆分 实施清单——分步任务 带 checkbox 的任务列表
changes/archive/<日期-名>/ 归档命令自动生成 历史审计——追溯决策 完整变更副本，一旦归档只读不删

二、核心概念：双文件夹模型

OpenSpec 的精髓在于两个目录的分工：

specs/ = Git 的 main 分支 —— 永远代表系统当前状态
changes/ = Git 的 feature 分支 —— 每个变更独立开发
archive/ = Git 的 log —— 历史记录，只增不减

三、增量规格的格式 —— 这是最关键的设计

changes/<名>/specs/ 里的 spec.md 不是一个完整的规格文件，而是相对于主 specs 的增量（diff）：

归档时，这三种标记分别执行不同的操作：

标记 归档时做什么
ADDED 追加到 specs/<领域>/spec.md 对应章节
MODIFIED 替换 specs/<领域>/spec.md 中对应的场景描述
REMOVED 从 specs/<领域>/spec.md 中删除对应场景

这就是 OpenSpec 的”合同”机制——每次变更都精确声明了对系统规格的增删改，人和 AI 都能看清楚变更范围。

四、多需求并行会不会乱？

隔离机制：一个需求 = 一个独立目录

每个 change 目录完全物理隔离，就像多个 Git feature branch 同时开发互不干扰。

冲突检测

如果两个活跃 change 同时修改了同一个领域（比如 add-2fa 和 fix-login-timeout 都在改 specs/auth/spec.md）：

  • 归档第一个 change 时正常合并
  • 归档第二个 change 时 OpenSpec 检测到冲突，要求解决后再归档

这跟 Git merge conflict 的逻辑一样。

六、历史文档越来越多，能删吗？

绝对不能删的

specs/ 是系统真相的唯一来源。删了它，后续增量就没了参照物，AI 不知道系统长什么样。

可以安全删除的

理由很充分：

  1. 规格已合并 —— archive 里的 delta specs 已经合并进 specs/ 了，删掉 archive 不影响系统运行
  2. Git 本身就是归档 —— 如果 proposal.md、design.md 都提交到了 Git，git log 随时能找回来
  3. archive 只是翻阅便利 —— 它是为了让回溯更快，不是系统运行的必需品

三种清理策略

策略 做法 适合场景
全保留 永久保留全部 archive 团队协作、合规审计、新人频繁入职
定期清理 保留近 3~6 个月，删除更早的 个人项目、日常迭代
依赖 Git 归档后立即删除 archive 纪律好、commit message 规范的项目

实操：在 CLAUDE.md 中约定清理规则

七、Q@a

Q1: OpenSpec 的 specs/ 和 changes/ 分别是什么？为什么这样设计？

答： 双文件夹模型是 OpenSpec 的核心设计。

  • specs/ = 系统当前真相，是稳定且经过审核的规格
  • changes/ = 活跃的变更提案，每个 change 独立隔离

这样设计的原因是模拟 Git 的分支模型：specs/ 像 main 分支，changes/ 像 feature 分支。一个反映”系统现在什么样”，一个记录”我们正在改什么”。两者分离保证了系统始终有一个干净的真相来源，同时允许多个变更并行推进。

Q2: OpenSpec 的增量规格（Delta Specs）是怎么工作的？ADDED / MODIFIED / REMOVED 分别做什么？

答： 增量规格是 OpenSpec 区别于传统 spec 工具的关键设计。

传统做法是每次变更重写整个 spec 文件，导致 diff 巨大且难以审计。OpenSpec 的做法是：

  • 每个 change 只写相对主 specs 的变化
  • ADDED 标记新增需求 → 归档时追加
  • MODIFIED 标记修改需求 → 归档时替换
  • REMOVED 标记删除需求 → 归档时删除

这样每次变更的影响范围一目了然，归档时自动合并，同时保留了完整的审计轨迹。

Q3: 多个需求并行开发时，OpenSpec 如何防止规格冲突？

答： 三层机制：

  1. 目录隔离 —— 每个 change 独立目录，物理隔离
  2. 按领域分组 —— specs 按领域（auth、payment、ui）组织，不同领域的 change 不冲突
  3. 冲突检测 —— 如果两个 change 改了同一个领域的 spec，后归档的那个会检测到冲突，要求人工解决

这跟 Git 的 merge conflict 机制同理。

Q4: 归档（archive）做了什么？为什么归档后的文档很重要？

答： 归档做了三件事：

  1. 合并 delta specs → 把 ADDED/MODIFIED/REMOVED 应用到主 specs，更新系统真相
  2. 移动目录 → change 从活跃区移到 archive/，带日期前缀
  3. 验证通过才放行 → tasks 必须全部完成

归档后的文档重要性在于：它提供了完整的变更审计追踪。三个月后有人问”为什么认证模块改成这样了”，翻 archive 里的 proposal.md 就能看到当时的决策理由，不需要翻聊天记录。

Q5: 如果一个项目的 openspec/changes/archive/ 已经堆积了上百个目录，怎么处理？

答： archive 是只读历史，可以安全清理：

  1. 最小风险方案 —— 保留近 3 个月 + 所有涉及架构决策的提案，其余删除
  2. 零风险方案 —— 如果项目 commit message 规范，Git 本身就是完整的归档，archive 全部可删
  3. 不能删的 —— specs/ 绝对不能动，那是系统真相

实践中关键是区分”系统需要的”（specs/）和”方便翻阅的”（archive/），前者不能丢，后者是缓存。

Q6: OpenSpec 和传统 PRD（产品需求文档）有什么区别？

答： 三个核心区别：

维度 PRD OpenSpec
受众 人（产品、开发、测试） 人 + AI 编码助手
格式 自由格式，word/wiki 结构化的 markdown，机器可解析
生命周期 写完就静态了 从 proposal → tasks → archive 全过程追踪

PRD 是给人看的说明书，OpenSpec 是给人和 AI 共同遵守的”合同”。PRD 写完放在那里积灰，OpenSpec 的 specs 是活的——每次归档都在更新。

Q7: 什么情况下用 OpenSpec 是过度设计？什么情况下不用它？

答： 不用 OpenSpec 的场景：

  • 单人玩具项目，没有长期维护计划
  • 一次性的脚本或工具
  • 不涉及功能变更的纯样式调整

需要 OpenSpec 的场景：

  • 中大型功能（涉及多个模块/文件）
  • 多人协作或长期维护的项目
  • 需要决策可追溯的团队项目
  • AI 编码助手重度使用的项目（没有 spec 约束 AI 容易跑偏）

判断标准很简单：如果三个月后你自己会忘记这段代码为什么这样写，那就值得写 spec。

Q8: OpenSpec 和 Superpowers 在实践中如何配合？

答： 两者的分工：

  • OpenSpec 管”死”的东西 —— 文件、结构、追踪。它保证每次变更都有结构化记录。
  • Superpowers 管”活”的东西 —— 对话、决策、纪律。它保证 AI 不跳过步骤、不走捷径。

实践流程：

  1. brainstorming（Superpowers）明确需求 → 输出到 OpenSpec 的 proposal.md
  2. writing-plans（Superpowers）拆解任务 → 回填到 OpenSpec 的 tasks.md
  3. TDD + 子代理执行（Superpowers） → 按 tasks.md 逐项实现
  4. 验证通过 → /opsx:archive 归档（OpenSpec）

两者不是竞争关系，是工件标准 + 行为纪律的互补。

Q9: OpenSpec 的 tasks.md 和 GitHub Issues / Jira 有什么区别？会重复吗？

答： 不同层级：

  • GitHub Issues / Jira = 协作层面，用于分配、排期、跨团队沟通
  • OpenSpec tasks.md = 实现层面，是 AI 编码助手的执行清单，粒度更细（具体的文件路径 + 代码变更）

实践中两者可以共存：Jira 上有个 Epic “添加 2FA 功能”，OpenSpec 里对应一个 change，tasks.md 是把 Epic 拆成 AI 可以直接执行的 bite-size 任务。不重复，是上下级分解关系。

Q10: 如果一个变更做到一半需求变了，OpenSpec 怎么处理？

答： 两种方式：

  1. 小改 —— 直接修改 delta specs 里的 MODIFIED 标记，重新 /opsx:verify 检查一致性
  2. 大改 —— 废弃当前 change 目录，创建新的 change。原来的 change 可以作为参考保留或删除

OpenSpec 的 change 目录是”施工中的提案”，在归档前随时可以改。归档之后如果需求又变了，就再创建一个新的 change，新的 delta 是相对已经更新后的主 specs 的——这跟 Git 再开一个 branch 改 main 上的代码是一样的。

八、总结

OpenSpec 的文档体系可以归结为三层：

核心原则：specs 是合同，archive 是收据。合同必须妥善保管，收据可以定期清理。

判断删不删的标准：如果删了这个目录后，新来的 AI 编码助手还能不能理解系统现状？能 —— 那它就是 archive，可以删。不能 —— 那它就是 specs，绝对不能删。
